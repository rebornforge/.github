## Français

# Plan de validation UX et arbitrages

## Ce qui a été fait

Consultation documentaire et synthèse heuristique ; vérification de cohérence avec le MVP approuvé. Aucun utilisateur interrogé, aucune maquette ou application testée, aucune mesure de préférence collectée. Les sources et échecs d’accès sont tracés dans le benchmark.

## Tests à préparer pour le prototype

Recommandation : séances courtes avec anciens utilisateurs, contributeurs et au moins un profil peu familier de GitHub ; le fondateur peut d’abord faire une revue de parcours, sans la présenter comme validation représentative. Aucun recrutement, prise de contact ou enregistrement autorisé implicitement.

Utiliser des données fictives identifiées. Demander de penser à voix haute sans expliquer la solution ; noter accomplissement, hésitations, erreurs et compréhension, pas seulement les clics. Toute collecte et conservation de notes personnelles doit être approuvée.

| Test | Tâche sans suggérer la navigation | Signal observé / lien |
| --- | --- | --- |
| T01 | Retrouver un ancien projet à partir d’un alias | Recherche et retour de filtre ; J01, US02 |
| T02 | Dire si une fiche autorise la réutilisation du code | Interprétation droits/histoire ; J01–J02, US03–US04 |
| T03 | Proposer une correction et expliquer quand elle sera publique | GitHub, aperçu, revue ; J03–J04, US05–US07 |
| T04 | Retrouver sa proposition après une demande de précisions | État et prochaine action ; J04, US07 |
| T05 | Signaler une erreur de droits sans publier de preuve privée | Compréhension de l’issue publique ; J06, US09 |
| T06 | Consulter une contribution FR depuis l’interface EN au clavier/mobile | Langue source, focus, filtres ; J07, US10–US11 |
| T07 | Examiner deux corrections concurrentes | Comparaison, version et décision ; J05, US08, US12 |

Résultat de chaque test : Non exécuté. Ne fixer ni taux de réussite inventé ni seuil statistique sur petit échantillon. Corriger en priorité blocages, risques de publication privée et confusion sur les droits ; suivre les constats avec source et sévérité.

## Questions à trancher à cette phase

- Retenir « Explorer / Comprendre / Contribuer » ou demander une autre terminologie.
- Retenir les initiatives liées et le filtre plutôt qu’un catalogue séparé.
- Retenir hiérarchie histoire/sources/droits et formulaire guidé.
- Accepter que les profils restent hypothétiques jusqu’aux tests de prototype.
- Confirmer les principes mobile, accessibilité et traduction.

Aucun changement au login GitHub, à la modération ou au périmètre de phase 1 n’est proposé. Les limites du canal de signalement et l’absence de compte alternatif restent visibles, conformément aux choix approuvés.

## Passage de phase

Le fondateur examine ce dossier et accepte ou amende les recommandations. La fusion de la PR reste distincte de la validation UX et de l’autorisation de phase 3. Après autorisation : trois vraies maquettes d’accueil distinctes — Digital Forge, Digital Heritage, Modern Community — avec intention, forces, limites, responsive et complexité. Aucun prototype ni code définitif à cette phase.

## English

# UX validation plan and decisions

## Completed work

Desk research and heuristic synthesis, checked against the approved MVP. No interviews, mockup/application testing or preference measurements. Sources and access failures are logged in the benchmark.

## Tests to prepare for the prototype

Recommend short sessions with former users, contributors and at least one GitHub novice. Founder walkthroughs can precede them without being called representative validation. No recruitment, contact or recording is implicitly authorized.

Use identified fictional data. Ask participants to think aloud without explaining solutions; record completion, hesitation, errors and understanding rather than clicks alone. Personal-note collection/retention needs approval.

| Test | Task without navigation hints | Observation / link |
| --- | --- | --- |
| T01 | Find an old project from an alias | Search/filter recovery; J01, US02 |
| T02 | Explain whether a record authorizes code reuse | Rights/history comprehension; J01–J02, US03–US04 |
| T03 | Propose a correction and explain when it goes public | GitHub, preview, review; J03–J04, US05–US07 |
| T04 | Find a submission needing clarification | State and next step; J04, US07 |
| T05 | Report a rights error without private evidence | Public-issue comprehension; J06, US09 |
| T06 | Read French content from English UI using keyboard/mobile | Source language, focus, filters; J07, US10–US11 |
| T07 | Review concurrent corrections | Comparison/version/decision; J05, US08, US12 |

Every test result: Not executed. Do not invent success rates or statistical thresholds for small samples. Prioritize blockers, private-publication risks and rights confusion; log evidence/severity.

## Decisions for this phase

- Adopt Explore / Understand / Contribute or request different labels.
- Adopt linked initiatives and filter instead of a separate directory.
- Adopt history/source/rights hierarchy and guided submission.
- Accept hypothetical profiles pending prototype testing.
- Confirm mobile, accessibility and translation principles.

No change proposed to approved phase 1 sign-in, moderation or scope. Reporting-channel and account limitations remain visible.

## Phase transition

Founder reviews and accepts/amends recommendations. PR merge is separate from UX acceptance and phase 3 authorization. After authorization: three distinct homepage mockups — Digital Forge, Digital Heritage, Modern Community — with intention, strengths, limits, responsive behavior and complexity. No prototype or final application code in this phase.
